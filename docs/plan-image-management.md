# 执行计划：图片文件管理系统

状态：方案已确认（2026-11-10），尚未开始实施。

## 目标

把现在“上传一张、处理一张、删了就没了”的图片功能，做成一套完整的图片文件管理系统：

- 批量上传快、状态清楚、失败可重试、重复可识别。
- 一张照片可以有多个版本（不同清晰度、不同格式、本地或外链），随时切换。
- 删除先进回收站，可恢复，到期自动清理。
- 服务器上的每个文件都有登记，孤儿文件和丢失文件能被发现和处理。
- 后台能看到存储占用，能下载原图、重新生成尺寸。

范围是所有本站托管的图片：照片、项目封面和截图、收藏海报、人物照片、品牌图、技术栈图标。照片拿到全部功能；其他模块共用底层的登记、回收站和扫描，不做版本。

## 现状和问题

| 方面     | 现状                                                              | 问题                                           |
| -------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| 上传     | 前端逐张串行；服务器把整个文件读进内存，同步生成 4 个 WebP 再返回 | 慢；排队中的文件也显示“上传中”；没有重试和取消 |
| 刷新     | 队列只在页面内存里                                                | 刷新丢队列，没有离开提醒                       |
| 重复     | ID 是文件名加随机字符，不看内容                                   | 同一张图传两次变成两张照片                     |
| 版本     | 一张照片一份图片；“替换图片”会删掉旧文件                          | 换不回去，不能并存多个源                       |
| 删除     | 直接删数据库记录和文件夹                                          | 没有回收站，误删无法恢复                       |
| 一致性   | 文件写完再写数据库；删除失败只记日志                              | 三种情况会留下孤儿文件，没有任何扫描工具       |
| 可见性   | 原图私有保存，但后台没有下载入口；看不到占用空间                  | 文件只进不出，无法管理                         |
| 其他模块 | 项目、收藏、人物的图片信息以 JSON 存在各自的行里                  | 没有统一视图，无法统一对账                     |

## 核心设计

### 1. 图片资产登记表（`ImageAsset`）

每一份落盘的图片（一个文件夹：若干 WebP 加一份原图）在数据库里有一行：

- 存储位置（`storageKey`）、归属（哪个模块的哪条记录、什么角色：照片版本、封面、截图、海报……）。
- 原图信息：文件名、格式、字节数、宽高、内容哈希（SHA-256）。
- 已生成的尺寸、总占用字节数。
- 状态：`ready`（可用）、`processing`（尺寸生成中）、`failed`、`trashed`（在回收站，带删除时间）。

这张表是整个系统的地基：去重靠哈希，回收站靠状态，孤儿扫描靠“磁盘上有、表里没有”，存储统计靠字节数。

现有图片通过一次回填登记进来（扫描现有记录和磁盘，计算哈希）。回填做成可重复执行的命令，不改已推送的迁移。

### 2. 照片版本（`PhotoVersion`）

- 一张照片有一个或多个版本。每个版本是“本站托管”（指向一个资产）或“只引用外链”（一个 URL），带自己的来源、宽高、EXIF 和一个可编辑的标签（例如“JPEG 预览”“PNG 无损”）。
- 照片记录一个“当前版本”。照片表现有的 `src`、`storage`、`storageKey`、`variants`、`width`、`height` 保留，作为当前版本的副本。这样公开接口、图片地址路由和静态应急快照都不用改。
- 切换版本是一次数据库事务：改当前版本，同步这几个字段。标题、日期、排序、可见性都不变。
- 非当前版本的文件只对已登录的管理员开放，访客拿不到。
- 每张照片默认最多 10 个版本，可以在后台“网站设置”里调整。
- 现在的“替换图片”改为“添加版本并设为当前”，旧版本保留，由用户决定是否删除。“转为本站托管”变成“给外链版本生成一个本站托管的版本”。
- 迁移：新增一个迁移建表，并为每张现有照片生成一个版本。

### 3. 上传管线

前端：

- 同时上传 2 到 3 张（服务器按 CPU 核数限制同时处理的数量，超出的排队）。
- 状态分清：等待中、上传中、处理中、已完成、失败、已跳过（重复）、已取消。显示整体进度。
- 失败的可以单个重试或全部重试；等待中和上传中的可以取消。
- 有未完成的任务时，刷新或离开页面会弹出提醒。
- 上传前在浏览器里算出文件哈希，连同文件名先问服务器是否冲突。冲突指内容完全相同，或原文件名相同。
- 有冲突时弹窗让用户决定，交互和 Windows 复制文件时一致：
  - **跳过**：不上传这个文件。
  - **替换**：新图片成为那张已有照片的当前图片，照片信息、排序和可见性不变。版本功能上线后，旧图片作为一个版本保留；上线前旧图片进回收站（回收站也未上线时按现有“替换图片”处理）。
  - **都保留**：作为一张新照片上传。
  - 勾选“对所有冲突执行此操作”后，本批剩余的冲突不再询问。
- 内容完全相同时“替换”没有意义，弹窗里只提供跳过和都保留。

服务器：

- 上传流式写入临时文件，不再整个读进内存（并发后内存占用可控）。
- 所有文件先写进暂存目录（`.staging/<上传ID>`），全部写完后一次改名到正式位置，再写数据库。启动时清空暂存目录。半截文件不会再出现在正式目录里。
- 每个文件带一个幂等键。网络超时后重试同一个文件，不会生成第二张照片。
- 记录每一步耗时（接收、解码、每个尺寸的编码、写盘），用真实数据决定下一步优化。

关于刷新：浏览器不允许页面在刷新后继续持有本地文件，所以还没发出的文件一定要重新选择。方案是让重新选择变得安全：服务器记录最近一批上传的结果，刷新后页面能看到哪些已完成、哪些失败；把整批文件重新拖进来，已完成的会因为哈希重复被自动跳过。

关于速度：主要耗时在 WebP 编码，最大的 3072 尺寸占一半。先做并发和耗时记录。如果服务器实测单张仍然很慢，再做“后台生成”：上传后只同步生成缩略图就返回，其余尺寸进入持久化的后台队列，照片在尺寸生成完之前不能设为公开，重启后队列继续。这一项放在后面，根据实测决定做不做。

不做分片断点续传：单个文件上限 40 MB，复杂度不值得。

### 4. 回收站

- 删除照片、删除某个版本、其他模块替换或删除图片，都先进回收站：数据库标记为已删除，文件原地不动。回收站里的图片对访客立即不可见。
- 回收站页面：缩略图、原归属、删除时间、占用空间；可以恢复、立即彻底删除、清空。
- 默认保留 30 天，可以在后台“网站设置”里调整，到期由每日维护任务彻底删除。彻底删除时先删文件再删记录，文件删除失败会在下次维护重试，不再产生孤儿文件。
- 删除被引用的照片（例如登录背景在用）时，确认框里明确提示。
- 第一步只有照片和照片版本支持“恢复到原位”。其他模块的图片进回收站后可以下载原图，恢复到原位以后再加。

### 5. 一致性扫描

后台提供“扫描文件”，也每周自动跑一次，只报告，不自动删除：

- **孤儿文件**：磁盘上有、登记表里没有。列出预览和大小，可以删除，或“认领”为一张新的隐藏照片。创建不到 1 小时的文件夹不算，避免误伤正在上传的文件。
- **丢失文件**：登记表里有、磁盘上没有。在对应照片上标出。如果原图还在，可以一键重新生成尺寸。
- **不完整**：缺某个尺寸或文件损坏。同样可以重新生成。

### 6. 存储管理页

后台新增“文件管理”：

- 总占用，按模块、按原图和生成尺寸分别统计；回收站占用；磁盘剩余空间。
- 最大的文件、最近上传、扫描结果入口、回收站入口。
- 单张图片的操作：下载原图、重新生成尺寸、查看所有版本和文件。
- 批量重新生成（以后调整尺寸或压缩参数时用）。
- 磁盘剩余空间低于阈值时，上传前提示。

### 7. 存储后端和部署约束

- 把 `LocalImageStore` 收敛成一个接口（写、读、删、列目录、取大小、改名），为之前计划的 R2 存储（Stage 19c）留好位置。这次不实现 R2。
- 公开图片地址（`/uploads/...`）的格式不变，静态应急快照和多区域发布不受影响。
- 回收站和暂存目录都在 `UPLOAD_DIR` 内。备份要求不变：上传目录和数据库必须一起备份。
- 安全规则不变：原图不公开、输出去掉 EXIF、隐藏照片的文件只给管理员、外链导入的 SSRF 防护。

## 分步

每一步单独提 PR 到 `dev`，带测试，数据库变更只新增迁移。

### 第 1 步：上传队列（不改数据库）

状态：已实现（2026-11-10），等待在生产服务器上实测耗时。日志里搜 `Photo upload timings`，字段是 `receiveMs`（接收）、`waitMs`（排队等处理）、`decodeMs`、`encodeMs`、`saveMs`。

并发上传、状态区分、重试、取消、离开提醒、整体进度；服务器流式接收、暂存目录加原子改名、并发限制、耗时日志。

完成标准：20 张图的批量上传总时间明显缩短；任何一张失败都能单独重试；中途杀掉服务器进程，正式目录里没有半截文件。

### 第 2 步：资产登记、去重、幂等

状态：已实现（2026-11-10）。和最初设想不同的两点：回填在服务器启动时自动在后台执行（可重复，已登记的跳过），不需要手动运行命令；“最近一批上传的结果”存在浏览器的会话存储里，刷新后再向服务器确认哪些其实已经传完。这一步只登记照片，其他模块在第 6 步接入。

新增 `ImageAsset` 和回填命令；上传前哈希查重；幂等键；最近一批上传的结果在刷新后可见。

完成标准：同一文件重复上传会被识别；刷新后重新拖入整批，只上传没完成的。

### 第 3 步：照片版本

状态：已实现（2026-11-11）。版本上限和回收站保留天数在“网站设置 → 后台管理 → 图片管理”里；保留天数从第 4 步起生效。

新增 `PhotoVersion` 和迁移；编辑页的版本列表（添加、切换、改标签、删除）；非当前版本只对管理员可见。

完成标准：同一张照片可以并存 JPEG 和 PNG 两个版本（本地或外链），一次点击切换，公开页面随之更新。

### 第 4 步：回收站

状态：已实现（2026-11-11），范围是照片和照片版本；其他模块的图片在第 6 步接入。入口在照片页右上角。每 6 小时清理一次到期内容，文件删除失败的保留在回收站里下次重试。

软删除、回收站页面、恢复、到期清理、引用提示。

完成标准：误删的照片能完整恢复（含所有版本）；到期后文件和记录都被清掉。

### 第 5 步：扫描和存储管理页

孤儿、丢失、不完整三类扫描；占用统计；下载原图；重新生成尺寸。

完成标准：手动往上传目录放一个无关文件夹能被发现；手动删掉一个尺寸文件能被发现并修复。

### 第 6 步：其他模块接入和按需优化

项目、收藏、人物、品牌图、技术栈图标的写入和删除改走同一套登记和回收站；根据第 1 步的耗时数据决定是否做后台生成。

## 已确认的决定（2026-11-10）

1. 回收站默认保留 30 天，可在网站设置里调整。
2. 上传冲突时弹窗询问，交互和 Windows 一致：跳过、替换、都保留，可对全部冲突生效。
3. 每张照片的版本上限默认 10 个，可在网站设置里调整。
4. 其他模块（项目、收藏、人物、品牌图、技术栈图标）纳入登记、回收站和扫描。
5. 后台生成尺寸先不做，等第 1 步的实测数据再定。

## 不能遗漏的后续事项

- **后台生成尺寸**：第 1 步上线后，在生产服务器上批量上传一次，读取耗时日志。把单张各阶段耗时和结论写回本文件，再决定做不做。做与不做都要在这里留下记录，不能不了了之。
